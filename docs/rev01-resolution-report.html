35 Admin Dashboards Manual A-field overrides shall NOT be retained. An Edit option must be provided to allow modification when needed. The current override shall be removed from Step 4 (e.g. clause 3.4.6, 3.4.7). Status: not completed (in 16.05 review). RESOLVED Phase 1

Behaviour change

Before: typing an A-field value made it "sticky" — future cascades from F/C wouldn't overwrite it. After: A-fields with an auto_source_field_id always re-derive from their source on every update, UNLESS admin explicitly locks the row via the Edit flow.

Mechanism

  • New is_manual_override boolean column on agreement_field_values (migration 003_manual_override_flag.py).
  • services/agreement_service.update_agreement_fields rewrites cascade logic: always recompute unless locked; backend guard drops drive-by writes that would clobber a locked row.
  • PUT /api/agreements/{id}/fields accepts an overrides: {field_id: true|false} map alongside values.
  • AppendixBuilder UI: per-row Edit button locks the override (amber "override" badge appears); Reset to Auto button clears the lock and re-pulls from source.
  • 3 new pytest cases cover: re-derive on source change (no override), lock holds through source change, reset-to-auto.

Scenario

Clause 3.4.6 (Interim Payment Days = C05 → A12): Admin enters C05 = "60 days PDC" → A12 auto-fills with "60 days PDC". Admin clicks Edit on A12 row, changes to "45 days PDC", saves — A12 now LOCKED with amber badge. Admin later changes C05 to "30 days PDC" — A12 stays at "45 days PDC" (override holds). Admin clicks Reset to Auto on A12 — A12 immediately becomes "30 days PDC" (cascaded from current C05).
